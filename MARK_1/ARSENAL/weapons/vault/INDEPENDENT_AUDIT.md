## Summary
The vault is a verifier-gated, TTL-aware verified-result memory store with three modules: vault_gate (admission logic), vault_store (persistence and read contract), and vault_router (tier classification). The selftest_all.py suite exits 0 cleanly with 3/3 suites PASS across all adversarial cases tested in the self-test (record-less writes demoted to LEAD, empty/whitespace/bool/int/None fields in verification records all rejected, stale facts flagged correctly, LEAD never returned in query_facts, copy-on-return mutation bypass blocked). The gate genuinely discriminates — it rejects bad inputs across 11 attack shapes in its self-test and accepted all independent adversarial probes attempted during this audit (dict method, list result, unicode whitespace, nested-empty record). Two real defects were found: the README Quick Start section cites a stale path that no longer exists after the repo restructuring, and the result/domain fields in gate_write are not type-checked (non-string values like int 0 pass silently), which is inconsistent with the strict string-type rail enforced on verification_record fields. Two disclosed limitations were confirmed: the disk-backed store trusts JSON on reload with no integrity verification, and v.entries is a mutable public attribute that bypasses the gate if the caller holds a direct reference to the Vault object — both are within the disclosed threat model but the entries-mutation hole is not mentioned in the README ceiling.

## Defects found (4)
1. README Quick Start has the WRONG path ('Expanding_Frontiers/weapons/vault') — the repo was restructured to MARK_1/ARSENAL/weapons/vault but the README was not updated. The correct command would fail silently with 'no such file' if followed literally.
2. v.entries is a public attribute with no access control. An external caller holding the Vault object can iterate and mutate stored entries directly (e.g., flip 'tier' from 'LEAD' to 'VERIFIED_FACT', set 'record_valid' to True), bypassing the gate entirely for the in-memory Vault. The copy-on-return fix (Defect 1) only guards the returned dict from write() — it does not protect the entries list from external iteration/mutation. HOWEVER: the AUDIT.md explicitly scopes the threat model as 'honest write-discipline, not a malicious attacker controlling the Vault object itself,' so this is a design boundary, not a hidden flaw — but it is not flagged in the honesty ceiling.
3. On-disk JSON reload trusts the stored tier without re-gating. A hand-edited JSON file that flips a LEAD's tier to VERIFIED_FACT will reload and be served by query_facts as a fact, with verification_method=None. This is explicitly disclosed in AUDIT.md as a known limitation ('out of scope for v0'), but there is NO integrity check, no warning logged on reload when record_valid=True but verification_record=None, and no reload-time validation. A stale-disk fact with NULL verification_record but VERIFIED_FACT tier is indistinguishable in query_facts output from a legitimately stored fact except that verification_method is None.
4. entry.result and entry.domain fields are not type-checked: gate_write accepts non-string values (integers, booleans, lists) for result and domain without raising. E.g., result=0 passes the None/empty-string check because the predicate is isinstance(result, str) and result.strip()=='' — a non-string bypasses both branches and is accepted. This is inconsistent with the strict type-rail applied to verification_record fields.
